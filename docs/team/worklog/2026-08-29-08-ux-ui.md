**The code-review findings, first, since one was flagged HIGH and genuinely wrong.**

1. **Day boundaries and day labels were computed in two different time zones — real bug,
   fixed.** `localDayIndex`/`localMidnights` used a hardcoded `STATION_UTC_OFFSET_MS`
   (always PDT, never DST-aware even for the station's own zone), while every label drawn
   on those same boundaries — the midnight gridline's weekday, the day-nav heading, the
   numbers table's day sections — rendered in the *viewer's* zone. For anyone outside
   America/Los_Angeles this could put a gridline under the wrong weekday and a table row
   under the wrong day heading; the table's own caption ("Station-local time") was
   already false regardless, since it rendered `displayTimeZone`. Fixed two ways: (a)
   `tide-chart-geometry.ts` now computes real `Intl`-based zoned midnights via
   `formatToParts`, not an offset — correct across a DST edge in any zone, not just this
   fixture's DST-free window; (b) deliberately anchored the chart's day/night structure —
   gridlines, the day-nav heading, and the numbers table (rows and headers both) — to the
   **station's** calendar day, not the viewer's, and said so on screen: the existing
   zone-mismatch note now adds "the day divisions ... follow the station's own calendar
   day." Rationale for station over viewer: a tide table is inherently about a place, the
   same way NOAA's own daily tables are dated by the station regardless of who reads them.
   Any single *instant's* clock time (drag readout, status grid, footnote) still converts
   to the viewer's zone — that promise was correct and untouched.
2. **`aria-valuetext` could fabricate a reading — fixed.** The visible height was already
   gated on `reading !== null`; the accessible name wasn't, so a screen-reader user could
   hear "0.00 ft" as a real reading with nothing shown to a sighted user for the same
   state. Now says "No tide prediction available at ..." when `reading` is null.
3. **Three more `unwrapSourced(x) : metres(0)` fallbacks, made consistent with the honest
   pattern already used elsewhere in the same file (skip/null, not fake zero).** Curve
   path-building now drops a point rather than plotting a fabricated 0m; the SELECTED
   marker (line, pill, dot) is now gated on a real reading and simply doesn't draw if
   there isn't one; the slack-window diamond now skips rendering, matching the sunrise/
   sunset marker's existing pattern one screen up. All three are provably unreachable
   today (`clampAt` always keeps `selectedAt` inside the loaded series, and `heightAt`'s
   range check is inclusive at both ends) — the fix is for the day a live fetch has a real
   gap, not a hypothetical today.
   Not touched, per the review's own scope: unit-conversion completeness, the ULP
   rounding fix, both hydration guards, the provenance ESLint rule — all already correct.
   The component-split suggestion (extract `tide-status-cells.tsx`/`tide-table.tsx`) is
   real and I agree with it, but a ~900-line-file restructure is a code-structure call
   (house rules: that decision belongs to the architect) and I didn't have a signed-off
   plan for it in this lane — flagging it rather than doing it unilaterally mid-polish-pass.
   Left undone; see "Still not done" below.

**1. Information hierarchy.** Founder's own glance test — "what's it doing, rising or
falling, how fast, is the next turn in daylight" — is now visibly the loudest thing on
the screen; everything else demoted or folded, nothing deleted.

*Promoted:* the "Next turn" status cell now says, e.g., "High · 2h 55m to high · after
dark" — the daylight/darkness fact used to only exist as background shading; now it
directly answers the stated glance test in the one cell built for it, reusing the same
`daylightSpans` phase lookup the shading and the aria-valuetext already used.

*Demoted:* the header readout (next to the date, above the chart) used to be a bordered
pill repeating height + time + motion arrow/word + rate context. The motion/rate part is
identical information to the "State" status cell directly below it, in a bigger, cyan,
higher-contrast cell — showing it twice in the highest-visual-weight row on the page was
exactly the accretion problem this pass was asked to fix. Cut it to height + time only
(the one thing worth a glance mid-drag, before the grid re-renders), and dropped the
bordered-pill/surface-raised styling for plain header text — it no longer needs a
box to hit its own contrast floor (7:1 clears on the card's own `bg-surface` too:
text-primary 15.84:1, tide-cyan is gone from here entirely now).

*Folded behind disclosures, not removed:* the marker legend ("Tide height / Selected
time / Estimated slack / Sunrise-sunset / shading key") is now a collapsed "What do the
marks mean?" `<details>` under the chart — true forever, needed once. Likewise the
zone-mismatch explanation, the "sun/moon times are calculated" disclaimer, and the raw
data-provenance footnote (sample count, retrieval time, station id, datum) are now one
"More about this chart" disclosure — three separate always-on caption paragraphs
collapsed to one optional one. Both new disclosures use `min-h-touch-floor` (48px) since
anything tappable gets that regardless of how minor it looks.

*Left alone by explicit instruction, not oversight:* day/night shading, sun markers, Now
button, units toggle, moon badge — all present, none redesigned. The moon badge
specifically stayed exactly where and how it was (small, muted, top-right) — it's
already visually tertiary and "leave in place" reads as literal.

*Not removed, per the brief:* cached-fixture badge, every `SourcedValue`
Interpolated/Estimated disclosure, the numbers table.

**2. The contrast decision — solved structurally, not traded.** The code comment above
the shading opacities claimed "the 4.5:1 text floor," which is plain WCAG AA — not this
project's 7:1 floor for required information (`06-accessibility-baseline.md` §1). Actual
measured problem: `text-muted` composited over the day band (`moon-pale` #E8D9A8 at
12% opacity over `surface` #121A20) is **4.88:1** — real, and under the floor.

Fixed by taking text off the shaded fill entirely, per the brief's own suggested
options, in two parts:
- The day/night `<rect>` is now clipped to exactly the plot's vertical span (`PLOT_TOP`
  to `PLOT_TOP + PLOT_HEIGHT`) instead of bleeding 14px above and 30px below it. The
  day-of-week gridline label and every hour-axis label used to sit inside that bleed —
  now they sit on the card's plain, unshaded `surface`, where `text-muted` already has a
  documented, accepted exception at 6.48:1 for exactly this category ("timestamps,
  labels, helper copy the reader doesn't make a decision from" — `01-foundations.md`
  §1.2's own note). Not a new pair, not a new exception — the existing one, applied
  correctly instead of accidentally violated by shading bleed.
- Every label that has to sit AT the curve's own height (H/L labels, sunrise/sunset
  labels, the NOW tag) can't be moved off the band — it's the whole point that it tracks
  the curve. Each now gets an opaque backing plate (new `labelPlate()` in
  `tide-chart-geometry.ts`, sized from a monospace per-character advance since a DOM
  measurement pass isn't SSR-safe) filled with `--color-background`, so the label's real
  background is a flat, known colour, not the composited band.

Measured (WCAG relative-luminance formula, computed, not eyeballed — script kept in the
scratchpad if it needs rechecking):

| Text colour | On composited day band (4.88:1 before) | On the `labelPlate` backing (`--color-background`) |
|---|---|---|
| text-muted | 4.88:1 — fails | **7.05:1** (documented in `01-foundations.md`) |
| text-primary | 11.92:1 | **17.24:1** |
| tide-cyan | 6.59:1 — fails | **9.53:1** |
| signal-orange | 5.07:1 — fails (not used as text here; SELECTED pill is opaque orange fill, unaffected) | **7.34:1** |
| amber-flag | 7.06:1 (passes, barely) | **10.21:1** |

Every colour actually used as text on a backing plate now clears 7:1 with real margin.
This product is dark-only by design (`tokens.json`'s own `$darkOnlyByDesign`; the
"dark-mode" media-query block in `tokens.generated.css` is byte-identical to the base
tokens) — there is one theme to report, not two, and I'm saying that plainly rather than
inventing a second table for a theme that doesn't exist.
