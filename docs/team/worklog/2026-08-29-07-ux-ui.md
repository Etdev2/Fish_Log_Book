Real bug first, then contrast. `npm run verify` green. Server still on
**http://localhost:3413/tides**.

**1. Hydration mismatch — root cause confirmed, not guessed.**
`use-local-time-zone.ts`'s `getSnapshot` read `Intl.DateTimeFormat().resolvedOptions().timeZone`
directly, unconditionally. `getServerSnapshot` returning `null` is NOT by itself a
guarantee the first client render matches the server — `getSnapshot` can still be called
on that same first render, before any `subscribe`/mount has happened, and there was
nothing stopping it from returning the real viewer zone right then. `useNow()` looks
like the same shape but is safe for a different reason: its `getSnapshot` reads a `ref`
that is only ever written inside `subscribe`, which React calls post-mount, never during
render — so it returns `null` no matter when it's called, until after mount. Rewrote
`use-local-time-zone.ts` to copy that exact ref-gated shape.

Audited everywhere else the viewer's environment reaches an attribute (grepped for
`Intl.`/`resolvedOptions`/`navigator.` across `src/features/conditions` and
`src/features/settings`). Every `format.ts` function takes an explicit `timeZone`
parameter and reads no ambient state itself, so `aria-valuetext` and everything else
built from `displayTimeZone` inherits the fix with no separate call site to fix. Found
one more real instance of the identical fault, unprompted: `settings/units.ts`'s
`useUnitPreference()` read `localStorage` directly in `getSnapshot`, which could
mismatch for a returning visitor who'd already chosen metres (their unit feeds
`formatHeight`/`formatRate` inside `aria-valuetext` too). Ref-gated identically.

**How I actually verified it, not just reasoned about it.** `npm run verify` cannot see
this bug class (confirmed — it stayed green through both the broken and fixed versions).
This sandbox has no browser automation library installed and I was not going to add one,
but the machine has a real Google Chrome install, so I launched it headless via its own
DevTools Protocol (system binary + Node 22's built-in `WebSocket` global — no new
dependency), pointed it at the running dev server's `/tides` and `/settings`, and
captured every console message for several seconds across three separate runs each.
Console was clean both pages, all three runs (only pre-existing font-preload warnings,
unrelated). As a sanity check on the harness itself, I deliberately re-broke
`use-local-time-zone.ts` to the old version and reran the same check — it did not
reproduce that specific warning in the CDP console capture, but the Next dev server's
own terminal log did show a real, separate, tiny hydration diff during that same run: an
SVG ray-glyph line coordinate differing in the 14th significant digit
(`127.16846047756633` vs `...31`), which is `Math.sin`/`Math.cos` not being guaranteed
bit-identical between Node's V8 (SSR) and the browser's V8 (hydration) — a genuine, if
extremely minor, separate hazard I hadn't known about. Fixed it defensively by rounding
those four coordinates to 2dp (invisible at this scale, and rounding collapses any
ULP-level cross-engine difference to the same string). Restored the real timezone fix
and reran the console check three more times clean.

I could read the browser console, in the end, by launching the actual system Chrome —
saying so plainly since it was not a foregone capability and needed a workaround.
