### 2026-09-04 | head-dev | 3h

- The founder asked for the legal shield in the app: a disclaimer and a privacy notice, so
  the app is honest about what it is before anyone relies on it. Three documents, wired in.
- Wrote them against what the code actually does, not a template. Read the sync path, the
  auth path, every geolocation call site, the dependency list, and every absolute URL in
  `src/` first. The result is a privacy notice that can afford to be specific: the log is
  on the device, there is no analytics or advertising anywhere, the boundary map draws no
  tiles so looking at where you are tells nobody where you are, species photos are bundled,
  and exactly two things leave the phone — Supabase (only if you sign in) and a NOAA tide
  request carrying a station id and a date range.
- `src/core/legal/documents.ts` holds them as data, in `core/` because they are content
  with no I/O. `documents.test.ts` then tests the privacy notice like the promise it is: it
  fails if an analytics or crash-reporting dependency is added, if any file gains a runtime
  fetch to an absolute URL, if a basemap tile layer appears, or if a species photo starts
  pointing at a remote host. A notice nobody can invalidate is how it stays true in March.
- The permanent notice (`src/components/legal-notice.tsx`) sits on every screen that gives
  an answer somebody could act on: Fish Legal home, today's limits, a species' rules, and
  all three ID tools, in the wording each one needs. It is not dismissible on purpose — a
  disclaimer you can switch off is absent the one time it mattered.
- The one-time acknowledgement on Fish Legal is stored as the accepted version string, not
  a boolean, so a substantive change asks again and a typo fix does not. It does not block
  the section: putting a modal between an angler and the rule they are trying to obey is
  the wrong trade, and the permanent notice already covers the screens that matter.
- Contact address and governing law are the one blank. `LEGAL_CONTACT.resolved` is false,
  and the documents render an amber note saying they are incomplete and the app is not
  ready for the public, rather than printing a plausible-looking address. Same stance the
  conditions code takes with "No verified data". A test pins the flag to the address in
  both directions.
- **A bug worth the writeup.** The acknowledgement asked again on every single visit.
  React Compiler is on, and it identifies hooks by NAME — `legalAcknowledgement.use()` is a
  member call, so the compiler did not see a hook, memoized the component as having no
  reactive dependency, and it never re-rendered when the store read localStorage. Nothing
  failed: no error, no warning, no failing test. Every other preference in the app happens
  to wrap `.use()` in a `useX` function, which is why nobody had hit it.
- Added it as tripwire §4, and the tripwire immediately found a second one:
  `alerts-page.tsx` read the alert preferences the same way. That is a real defect on a
  screen the founder had already reported as broken — the four alert toggles showed
  defaults on every visit no matter how often they were changed. Fixed the same way, and
  confirmed in a browser that a toggle now survives a reload.
- My own first test of the acknowledgement gave a false pass: it counted the first-visit
  heading, which also disappears when the card correctly switches to the changed-version
  wording. Rewrote it to read the heading text.
