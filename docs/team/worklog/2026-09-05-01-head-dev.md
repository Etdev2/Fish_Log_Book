# 2026-09-05 — Head Dev — the flush had no sign-in trigger

Brought `head-dev/session-on-flush` (#48, open since 3 September) up to date with main —
merged rather than rebased, so the review history survives — and then went looking for
why a real trip would still end with everything queued.

The outbox drained on three events: a local write, `online`, and the tab becoming
visible. The sequence a trip actually produces is none of them. You log fish offshore
with no signal; you come home; you open the magic link; the tab is new, so
`visibilitychange` never fires, and the phone was already on wifi, so `online` never
fires. The day's catches sit queued behind a badge reading "Saved on this device" with
a working server on the other end. It drains only if the angler happens to switch apps
and come back — which nobody would think to do, because nothing tells them to.

So `installFlushListeners` now also binds the session and subscribes to
`onAuthStateChange`; a session appearing is a flush trigger. Signed out, it attempts
nothing, which is honest — `flushOnce` already stops the pass on the first
`auth_expired`, so the old behaviour would have burned one attempt per cold load for no
reason. `run-flush.test.ts` pins the trigger set; removing either line fails two of its
three cases, checked by removing them.

## What the schema was actually tested against

All 37 migrations applied in order to an empty Postgres 16 with Supabase-shaped roles
(`anon`, `authenticated`, `service_role`, an `auth.users` table and an `auth.uid()`
reading the JWT claim), plus Supabase's default grants on `public`. Against that:

- the signup trigger creates the `angler` row on `insert into auth.users`;
- a full catch — species, length, weight, `tags`, `favorite`, `quantity`,
  `regulation_snapshot` — inserts as `authenticated` with RLS on;
- a second angler sees 0 rows, `anon` sees 0 rows;
- an insert stamping someone else's `angler_id` is refused by the policy.

`postgrest-payload.ts` was diffed column-by-column against `information_schema` for all
nine synced tables: nothing in the allowlist is missing from the schema, so no
`PGRST204`. The columns the DB has and we don't send are all server-computed —
`updated_at`, `geo_cell_1km`/`geo_cell_10km`, the station distances.

None of that touches the network. PostgREST, the magic link, and the JWT are still
unproven; step 3 of `docs/development/supabase-project.md` is the only thing that
proves them, and it needs a person with a phone.

## Worth doing next, not done here

a build failure instead of a 400 in someone's network tab. I flagged the same thing on
#67 for a different reason. `test-agent/tournament-migration-guardrails` may already
cover it — check there before building it twice.
